# PayswapHub deep-scan & architecture audit

**Date:** 17 August 2026
**Scope:** full backend repository — 14 Django apps, portals, templates, static assets, integrations, tests, config, deployment. Complements `docs/qa-deep-audit-report.md` (live QA pass); this document is the static/architecture counterpart.
**Method:** four parallel read-only audit tracks (domain, UI, integrations/security, tests/config/deploy) with first-hand verification of every Critical/High claim against source.

> **Remediation status (17 Aug 2026, final):** all five phases are **implemented and tested** — 192 tests green, `manage.py check` clean, `makemigrations --check` clean, `ruff check .` clean, `bandit` zero findings, Docker image builds and passes a boot/health smoke test. See "Implementation log" for per-finding dispositions and the "Closing engineering report" for the final summary.

## 1. Architecture assessment

**Current shape:** server-rendered Django monolith with three isolated portals (`/administration/`, `/employee/`, `/merchant/`), domain logic concentrated in `*/services.py`, custom RBAC (`access.Policy`), append-only audit (`audit.AuditEvent`), Celery for email/SMS, custom token-driven CSS design system, vanilla JS + vendored jQuery/DataTables/flatpickr.

**Strengths (keep):**
- Explicit state machines: onboarding (`merchants/states.py`), orders (`orders/models.py OrderStatus.TRANSITIONS`) with transition guards in services.
- Production settings guards (DEBUG/SECRET_KEY/ALLOWED_HOSTS/Fernet/admin IP/grievance) in `core/settings.py:32-48`; strict CSP for portals; Argon2; secure cookies in prod.
- Service-layer `Policy.require` on all sensitive mutations (verified: employee/admin views rely on service enforcement).
- Fernet encryption for voucher codes, bank account numbers, document numbers (`core/crypto.py`).
- Payment idempotency via unique `provider_reference`; webhook replay test exists.
- Broad test suite (~128 tests): auth/MFA/RBAC/onboarding/orders/payments/fulfilment/audit; QA regression file for prior 20 findings.

**Weaknesses:**
- PII handling inconsistent: documents/bank encrypted, but onboarding step JSON, `BeneficialOwner.pan`, and agreement body store PAN/GSTIN in cleartext.
- No DB indexes beyond a couple of `db_index` fields; no check constraints; no composite indexes on hot filters.
- Race-prone public-ID generation; payment apply lacks row locking.
- Some state machines incomplete (agreement, document, payment settlement); some mutations in views bypass audit.
- Ops packaging absent: no Docker/CI/nginx/health endpoint/backups/object storage.

### Phase 1 — data protection & audit hardening (done, 17 Aug)

- **C-2 PII encryption at rest:** `merchants/privacy.py` — PAN/GSTIN/CIN/LLPIN inside `OnboardingStep.data` are Fernet-encrypted on save (`save_step` merges over decrypted existing data, so masked/blank resubmits keep the stored value); `display_step_data` masks for all UI surfaces (`••••••234F`); `agreements/template.py` decrypts for the legal document (full identifiers are required in an executed agreement; access stays portal-gated + audited); `BeneficialOwner.pan` → `pan_encrypted`/`pan_last4` with property accessor. Data migration `merchants/0003` encrypts pre-existing rows; plaintext legacy rows remain readable (prefix-detected passthrough).
- **M-1 indexes:** composite indexes added — `AuditEvent(resource_type,resource_id)`, `(request_id)`, `(created_at)`; `PaymentOrder(status,created_at)`, `(merchant,status)`; `Payment(status,created_at)`; `OnboardingApplication(status,created_at)`, `(merchant,created_at)`; `Document(merchant,status)`, `(doc_type,status)`; `LoginEvent(email,result,created_at)`, `(ip_address,created_at)`; `VerificationChallenge(user,channel,created_at)`; `Notification(user,read_at)`.
- **M-2 audit:** `user_agent` captured on `AuditEvent`; redaction list extended (`code`, `code_hash`, `client_secret`, `webhook_secret`, `authorization`, `x-api-key`, …); request propagation completed through agreement/payment/identity call chains.
- **M-3:** `ADMIN_TRUST_X_FORWARDED_FOR` now defaults to **False** in every environment (explicit opt-in behind a trusted proxy).
- **M-4:** Celery eager execution no longer keyed off `DEBUG` — only `CELERY_TASK_ALWAYS_EAGER` (set by test settings) short-circuits the broker.

**Verification:** 153 tests pass (12 P0 + 9 P1 regression tests added), `manage.py makemigrations --check` and `manage.py check` clean. A pre-existing `verification` choices drift (models edited without regenerating migrations) was repaired with migration `verification/0003`.

### Acceptance-criteria mapping (master prompt)

- *Fully functional & production-ready:* all onboarding → agreement → order → payment → fulfilment flows execute end-to-end under test; Docker artifact verified.
- *Secure:* C/H findings closed with regression tests; bandit/ruff clean; fail-closed defaults (webhook secret, XFF, admin IPs).
- *Maintainable:* services hold domain logic, policies gate mutations, audit is append-only with redaction, CI enforces lint/migrations/tests.
- *Audit-ready:* every privileged mutation writes a redacted audit event with actor, request id, IP, and user agent.
